## Questions
Cite file:line for every claim. Mark what you could not confirm as UNVERIFIED, and Android framework behaviour you recall but did not check as FW-MEMORY.

1. **Entry points**: every manifest component (activities, activity-aliases, services, receivers, providers, the Application class) with exported flag, intent filters (launcher, VIEW/deep links, SEND/share, file types, widgets, shortcuts, search), launchMode, dialog themes, configChanges. Use a merged manifest under the module's build/intermediates if one exists, otherwise src/main plus the built flavor.
2. **First-run flow and setup gates**: what a new user must do before the main UI is usable (intro/onboarding, permission prompts, password/vault/database/account creation, login, data import), with the code that enforces each gate. Using the per-class JaCoCo data, which screens did the baseline never reach, and which gate most likely stopped it? What would a test harness have to prepare (files, settings, accounts) to reach the rest of the app?
3. **Screens and navigation**: every activity, fragment, dialog/DialogFragment, popup and context menu, action mode, preference screen, bottom sheet, drawer, tab/pager; how the user moves between them (intents, fragment transactions, navigation graphs, drawer/tabs, back stack). For each window, the modes that change which handlers or menu items are active (selection/action mode, empty vs non-empty, loading vs loaded, locked vs unlocked, edit vs view, search). Then propose a candidate page list (S_<NAME>, one-line description, window class, mode predicate). Aim for tens of pages for a small app and up to about 150 for a large one; do not make one page per widget.
4. **Framework mechanisms** that will need framework, async or lifecycle edges: list/recycler/pager adapters, LiveData/ViewModel, RxJava, AsyncTask/executors/Handler, WorkManager/JobScheduler/AlarmManager, services (foreground, bound), broadcast receivers, content providers, data binding, the database layer, WebView/JS bridges, the Storage Access Framework and file pickers, notifications and their actions, home-screen widgets. Name the main app classes involved.
5. **Unreachable-code candidates**: classes or methods with no apparent caller (search references across the compiled sources and resources), debug-only or flavor-only code that is compiled in, sample/test helpers in the main source set, features gated by API level, hardware, network, accounts or build config. Give the evidence; do not decide final verdicts.
6. **Decomposition**: Propose 2-4 feature areas that separate agents can model in parallel with minimal overlap. For each area: the packages/classes it owns, its approximate method count (from the JaCoCo report), the pages it owns, its entry edges from other areas, and which area owns shared infrastructure (base classes, singletons, utilities, the database layer). Every compiled class must belong to exactly one area; list leftovers explicitly.
7. **Baseline coverage by area and screen**: per proposed area, methods hit by Monkey only, APE only, both, neither; the screens the baseline never reached and the likely reason.
