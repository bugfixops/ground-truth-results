# hash-checker — lessons

- **The built flavor matters more than the file name.** `MainActivity.java` exists only under `src/thirdPartyStores/`, not `src/main/`. A source index that prefers `src/main/` or the shortest path silently picks the wrong flavor (here it would have picked googlePlay); the standard configuration is the thirdPartyStores debug build, and every citation must resolve against it.
- **Bytecode line citations need range-aware checking.** javac attributes a `new` inside a chained call to the previous line, and a `new` inside a multi-line expression to the expression's first line (for example the call `App.onCreate -> ThemeHelperModule.<init>` is on `App.java:74`, where the line table put it on 73). Fifteen citations were corrected this way; a single-line token check flags these falsely.
- **Legacy `DEAD` / `FRAMEWORK_ONLY` dicts are not leftover failures.** The build converts them to UNREACHABLE entries and clears them (graph_def.py 63, 79, 684-706), and the built trigger JSON contains neither key. Grep counts on `graph_def.py` alone mislead; the built JSON is the check.
- **`scan_unreachable.py --callers` flags are the expected clean result when explained.** The 4 flags here are virtual dispatch that never reaches a base implementation (the `BaseFragment` pair) and SUPPRESSed closed-by-configuration edges (`getThemeAnalogue`, `setRefreshSelectedFileStatus`). Four flags, all explained, is clean — not a failure to fix.
- **A redrawn sample with the same seed returns the same methods when the graph is unchanged.** The redrawn final 30 equal the earlier final 30, and the redraw error rate (0/30) must not be confused with the historical rate (13/37, 0.351) from before the fixes landed in `graph_def.py`.
- **Framework claims written from memory must be replaced, not patched.** The 126 FW-MEMORY edges were handled one by one: 49 FW-SRC citations now point at Android 8.1.0_r1 lines that were printed and read, and every claim about androidx, ORMLite, SQLiteOpenHelper, the picker app or the JVM is written as INFERRED with what was not read.
- **A route starting from the plain launcher can hide a start-by-another-app data dependency.** Four checked paths started with the plain launcher entry but needed data only a start by another app carries (the VIEW / SEND URI and the two launcher shortcuts). The fix is to give the other-app start its own context (`@XURI`, `@XTEXT`, `@XFILE`) from the entry edge down to `onViewCreated`, not to keep the launcher tap in the notes.
