# Vanilla-Music: what reading the routes and citations found

- **A method shared by sibling subclasses that don't override it needs a context variant per subclass, or routes leak between them.** `LibraryActivity` and `FullPlaybackActivity` both inherit `onResume` from `SlidingPlaybackActivity`; `MiniPlaybackActivity` and `AudioPickerActivity` both inherit it from `PlaybackActivity`. Attaching the "enters S_LIBRARY" / "enters S_FULL" / "enters S_MINI" / "enters S_PICKER" edges directly to the one shared, un-suffixed impl node let the cheapest-route search enter through one activity (the launcher) and exit through a sibling's screen with no gate anywhere on the route — a silent, structural error that a 20+-step route can hide for a long time (it surfaced on the very first sampled route). The fix is the same context-variant mechanism already used for branch-dependent methods (`@LibraryActivity`, `@FullPlaybackActivity`, ...): the shared bytecode body gets copied onto every variant automatically, only the diverging tail needs separate hand edges. Worth checking for in any app where a `lifecycle()`-wired callback is shared by activities whose subclass tree only forks above the overriding class.
- **A citation can be "close enough to work" and still be wrong.** Eight framework edges (MediaAdapter's row-reading callbacks) all cited `LibraryPagerAdapter.java:895` — a real line in the file, inside a real method (`onItemClick`), just the wrong method; `check_citations.py` cannot catch this because the file and line both exist, only reading the printed snippet against the trigger text ("the tab's ListView reads the rows") shows the mismatch. A line number that resolves to *something* is not the same as resolving to the *right* something.
- **Guard-less bytecode edges cluster on touch-event state machines.** All three found this session were on the same `onTouch(Event)` dispatch chain of the vendored drag-sort-list library (`DragSortController.onTouch`, `DragSortListView.onTouchEvent`, `onDragTouchEvent`) — `ACTION_UP`/`ACTION_DOWN` switches with an `if (mDragState == ...)` guard immediately inside each case are exactly the shape `extract_calls.py` cannot see. Once one guard-less edge turns up on a state-machine method, it is worth checking that method's other outgoing bytecode edges too, not just the one the sample happened to pick.
- **`tools/show_route.py` crashes on its own established house style.** Its evidence-reference regex (`[^\s;]+`) assumes a `SRC File.java:N-M` citation has no internal whitespace, but the file's own style (and `SCHEMA_V2.md`'s own example) routinely writes multi-range citations as `N, M-K` with a space after the comma; the regex then truncates at the space and crashes `int('')` on the dangling trailing comma. (openlauncher's session hit and reported the identical bug.) Confirmed non-fixable in scope (`work/tools/` is out of bounds); worked around with a local read-only copy in the scratchpad that only changes the reference-splitting rule, so every route in the sample could still be read end to end against the real cited lines.
- **A stub loop that never calls its own body builder is a silent zero, not an error.** `for cb, why, ev in ((...),): pass` (meant to wire `PlaybackService.onSharedPreferenceChanged`) produced no edge at all and no build-time symptom beyond the method staying unreached — `build_graph.py` has no way to tell "a loop that does nothing" from "a loop the author meant to leave empty." Worth a visual double-check of any loop whose body is just `pass`.
- **`scan_unreachable.py --all --callers`'s 3 flagged callers were each already explained in the method's own reason text** (the `LiftAnimator` and `removeItem(int)` UNREACHABLE reasons already name their one bytecode caller and explain why it never actually invokes them) — the check is still worth running, since an unexplained caller would be a genuine gap, but a well-written reason during classification means the follow-up check is a fast confirmation, not new work.
- **`check_bytecode_lines.py`'s callee-name heuristic does not fit a `REGISTER` edge for an implicit `this`-as-listener registration** (`builder.setSingleChoiceItems(items, mode, this)`: the callee is `onClick`, but the word "onClick" never appears near the call). The codebase already had a workaround in place for the identical pattern one dialog over (`PlaylistDialog.onCreateDialog -> onClick` cites a line *range*, which the checker's single-line regex does not match at all); recognizing that precedent avoided mis-"fixing" a citation that was already pointing at the right line.
- **Tool coverage (Monkey/APE) can "run" a method with zero source-confirmed callers** (`Song.compareTo`/`toString`, two DragSortController/DragSortListView API methods) — `sanity_check.csv` flags these as contradictions by design, and the schema is explicit that tool coverage never sets a label; re-grepping confirmed no caller exists in either the app or the bundled library sources, so all four stayed UNREACHABLE.
