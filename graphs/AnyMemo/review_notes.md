What was reviewed by hand (class level, from method names, the manifest, layouts, the generated Dagger code and the fixtures on the baseline device):

- **Dagger 2.** `DaggerAppComponents`, `*_Factory`, `*_MembersInjector`, `AppModules`, `ActivityModules` are part of the method universe. The `@Provides` methods and `@Inject` constructors hang below `AMApplication.onCreate` (`INFERRED` root: the object graph is built when the application starts); the component's `inject(...)` methods are reached by class-hierarchy dispatch from the activities' `activityComponents()` calls. Because every activity builds its component through `ActivityComponentsBuilder.build`, many routes in `methods.csv` pass through `BaseActivity.activityComponents`; read those paths as "some screen of the app needs the injected component", not as a tap sequence.
- **ORMLite.** The DAO classes `DeckDaoImpl` and `FilterDaoImpl` are named in `@DatabaseTable(daoClass = ...)` and constructed by `DaoManager.createDao`; the generator links them from every `DaoManager` call (`INFERRED`).
- **Environment gates (edges into these classes carry `env`):** the Dropbox / OAuth cluster (`Dropbox*`, `Oauth*`, `UploadDropbox*`: needs a Dropbox account and the network), the deck downloader (`AbstractDownloaderFragment`, `AnyMemoDownloaderFragment`, `DownloadItem`, `DownloaderUtils`: needs the download servers), the home-screen widget (`AnyMemoWidgetProvider`, `WidgetRemoteViewsFactory`, `UpdateWidgetService`, `AlarmReceiver`: needs a widget on the launcher or an alarm). Content providers (`CardProvider`, `DatabasesProvider`) are only called from other apps, so their operations carry `env` unless the app itself calls the same `ContentResolver` operation.
- **Fixture gates (`needs_state`):** the importers for Mnemosyne, SuperMemo, QA-text and zip files need a file of that format; the Download fixtures (19 files) hold `table.csv`, `archive.zip` and others, but no Mnemosyne, SuperMemo or QA-text file.
- **Not gated, never run (UI actions nobody took):** the baseline did open decks (`StudyActivity` 49 of 56 methods, `QuizActivity`, `PreviewEditActivity`, `CardEditor`, `CardDaoImpl`, `OpenActionsFragment` ran), but never tapped **List** or **Card player** in a deck's action sheet (`OpenActionsFragment$1.onClick` ran, its `CardListActivity` and `CardPlayerActivity` branches did not: `CardListActivity` 0 of 66 methods, `CardPlayerActivity` 0 of 24, plus `CardPlayerService`, `CardPlayerContext`, `CardPlayerState`, `CardPlayerFragment`, about 65 methods in all). The same holds for the "swap question and answer" dialog of the preview screen and the card exporters. These are one or two taps from a deck, so they stay `REACHABLE`.
- **Branch gates read from the source at the frontier (`CFG['EDGES']`):** `MiscTabFragment.onActivityResult` (a file or folder returned by the system document picker: `env`, the baseline runs could not start other packages) and the text-to-speech completion callback (`AnyMemoTTSImpl$2.onUtteranceCompleted`: a TTS engine must speak: `env`).
- **Dead code** is mostly entity accessors that nothing calls (`Deck`, `Filter`, `Card`, `Category`, `Option`, `Setting`, `LearningData`), the unused `OauthAccountActivity` / `OauthAccessCodeRetrievalFragment` pair, three generated view-binding classes (`DropboxListActivityBinding`, `MainTabsBinding`, `UploadDropboxScreenBinding`: the `inflate` / `bind` factories are never called, the app goes through `DataBindingUtil`), and unused utility methods.
- **Open intent.** `AnyMemo.loadUiComponents` (called from `onCreate`) calls `handleOpenIntent` only when the launch intent action is `ACTION_VIEW` (a deck file opened from another app), so that edge carries `env`; it used to be the shortest route to many screens (the preview screen opened from the loader callback). Other routes to those screens go through the recent-deck list and the file browser.
