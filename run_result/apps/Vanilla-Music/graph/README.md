# Vanilla Music 1.3.2: method-level trigger graph (schema 2)

How every method of **Vanilla-Music** is triggered, in the standard configuration: the instrumented debug build (`vanilla-music/vanilla@1.3.2`, commit `2e7ef1ce402f`, APK sha256 `b728fc87...`), an API 27 emulator, permissions and fixtures as in `final_java_only`. Labels follow `handoff/SCHEMA_V2.md`: REACHABLE or UNREACHABLE, ENV and STATE gates, edge classes (explicit, standard, non-standard), and how each label was confirmed.

## What is in this folder

| File | What it is |
|---|---|
| `vanilla_trigger_graph.json` | pages, methods, `verdict`, `labels` (per-method fields), `edges` (with `edge_class`, `env_kinds`, `state_kinds`, stable ids), `paths` (verified paths only), `verification` (counts) |
| `methods.csv` | one row per method: verdict, UNREACHABLE reason, ENV and STATE kinds and texts, edge classes on the best route, whether an explicit/standard-only route exists, how the label was confirmed, path status, and the derived best route (`shortest_path`, `route_edge_ids`) |
| `../verification.csv` | the audit log: one row per label, edge or path that was checked, with result, how, and where (file:line) |
| `sanity_check.csv` | tool coverage (Monkey / APE, API 27) next to the labels; a one-way check only, it never sets a label |
| `vanilla_trigger_graph.html`, `build_report.txt` | the viewer and the validation report |

- Edge classes: explicit 2618, non_standard 52, page 128, standard 631. Non-standard edges: 52 (androidx MediaSessionCompat calls the Callback; androidx ViewPager calls the OnPageChangeListener; androidx ViewPager calls the PagerAdapter; androidx ViewPager.onRestoreInstanceState calls PagerAdapter.restoreState; androidx ViewPager.onSaveInstanceState calls PagerAdapter.saveState; the <fragment>).

## What the re-audit changed (compared with the schema 1 graph)

- **Labels.** The schema-1 generated draft (kept as `generated_draft_graph_def.py.txt`, never built) is superseded entirely by a hand-written `graph_def.py`: 1473 methods, 1325 REACHABLE / 148 UNREACHABLE, each UNREACHABLE method with a kind (`no_trigger_in_app` 144, `branch_never_taken` 4), a reason and a source reference — no `DEAD` / `FRAMEWORK_ONLY` remain (`grep -c "DEAD\|FRAMEWORK_ONLY" graph_def.py` is 0). 1158 labels are `SOURCE`, 315 `INFERRED` (almost all the INFERRED ones are the androidx ViewPager / MediaSessionCompat callback dispatch and the JVM static-initialiser rule, neither of which has source in this tree).
- **A real reachability bug found by sampling, not by construction.** `LibraryActivity` and `FullPlaybackActivity` both inherit `onResume` from the same un-overridden method (`SlidingPlaybackActivity.onResume`); `MiniPlaybackActivity` and `AudioPickerActivity` both inherit it from `PlaybackActivity.onResume`. The schema-1-era edges attached the "enters S_LIBRARY" / "enters S_FULL" / "enters S_MINI" / "enters S_PICKER" transitions directly to these shared, un-suffixed nodes, so a derived route could enter through one activity (the launcher, the cheapest start) and exit through a sibling activity's screen with no gate at all — found while reading the very first sampled route (`FolderPickerAdapter$Item.<init>`, which surfaced a route through `LibraryActivity.<init> -> ... -> S_FULL`, FullPlaybackActivity's screen, after a plain launcher start). Fixed with four context variants (`@LibraryActivity`, `@FullPlaybackActivity`, `@MiniPlaybackActivity`, `@AudioPickerActivity`); the shared bytecode body of each method (the `updateElapsedTime` call, the `super.onResume()` call, the `PlaybackService` lookups) is copied onto every variant automatically by the builder, only the four screen-specific "enters" edges and four lifecycle edges needed to be rewritten by hand. This one structural fix is why 19 of the 30 sampled paths are logged `fixed` rather than `correct` in `verification.csv`: their route passes through one of the four variants.
- **Guard-less bytecode edges on the vendored drag-sort-list touch dispatch** (`com.mobeta.android.dslv`, bundled as app source). Three edges auto-extracted from bytecode had no guard even though the enclosing code is conditional: `DragSortController.onTouch -> DragSortListView.stopDragWithVelocity` (only on `ACTION_UP` with `mRemoveEnabled && mIsRemoving && x > removePoint`), `DragSortListView.onTouchEvent -> onDragTouchEvent` (only while `mDragState == DRAGGING`), and `onDragTouchEvent -> stopDrag(boolean)` (only on `ACTION_UP` while still `DRAGGING`). All three got a guard and a STATE gate; the best route to `SongTimeline.removeSongPosition` now goes through the plain drag-to-sort-then-animate-remove path instead, where every step already carried a guard.
- **A stale citation, not from this session, caught by reading a route.** The framework edges wiring `MediaAdapter.getView` / `getCount` / `getItem` / `getItemId` / `hasStableIds` and the three fast-scroll callbacks from `LibraryPagerAdapter.instantiateItem` all cited `LibraryPagerAdapter.java:895`, which is a line inside `onItemClick`, not the `view.setAdapter(adapter)` call (the real trigger, at line 353, common code right after the per-tab switch). Re-cited to 353 for all 8 edges.
- **A `check_citations.py` problem, not from reading a route.** `ListPreferenceSummary`'s `onDialogClosed` edge cited `core/java/android/preference/ListPreference.java:331-340,352-356`; that file has only 355 lines, and those line numbers actually sit inside the unrelated `SavedState` inner class (a leftover from an earlier draft of the citation). Re-cited to the real `onPrepareDialogBuilder` (253-264) and `onDialogClosed` (277-283) lines, which were printed and read before citing them.
- **A citation this session itself introduced and then had to fix.** The new `LibraryActivity$1.run -> BottomBarControls.setCover` edge first cited line 578 (the `public void run() {` line of the anonymous `Runnable`); the actual call is on line 579. Caught by `tools/check_bytecode_lines.py` / by reading the route and comparing the printed line against the trigger text.
- **A `tools/check_bytecode_lines.py` false positive, not a wrong citation.** `LibraryActivity.onOptionsItemSelected@SORT -> LibraryActivity.onClick(DialogInterface,int)` (a `REGISTER` edge: `builder.setSingleChoiceItems(items, mode, this)` passes the activity itself as the dialog's click listener) cited the correct line (904), but the checker's heuristic looks for the literal callee method name ("onClick") textually on or near the cited line, which an implicit `this`-as-listener registration never has. The sibling edge `PlaylistDialog.onCreateDialog -> PlaylistDialog.onClick` (same `REGISTER` pattern) already worked around this by citing a line *range* rather than a single line, which the checker's single-line regex does not match at all; applied the same range citation here (902-904) rather than mis-"fixing" the line number itself.
- **Reflection / XML-instantiated classes reclassified `non_standard`.** 20 edges whose evidence already said "through reflection" (the `<fragment class=...>` XML tag for `ShowQueueFragment` in two layouts, the `PreferenceActivity` header-fragment list, the three nested `PreferenceScreen` fragment attributes of `preference_audio.xml`, and the three custom-`Preference`-row XML tags) were still on the default class; set to `non_standard` with a `via` text, per the schema's rule for views/fragments instantiated from layout XML.
- **9 edges correctly left `standard` after review.** `ShortcutPseudoActivity.onCreate -> PlaybackService.onStartCommand@ACTION_X` matched the same "mentions a library/reflection hint" regex only because the trigger text contains `setAction(`; these are explicit-component intents (`new Intent(this, PlaybackService.class)`), and the action is read only by the app's own `onStartCommand` switch, never used by the OS to resolve the target — correctly `standard`, set explicitly (with a comment) so the check records that it was reviewed rather than silently re-flagging it every build.
- **~40 methods newly classified `UNREACHABLE`** after a `grep -rn` over the whole app and library source tree found no caller: dead API surface of the bundled drag-sort-list library (unused constructor overloads, unused getters/setters, the whole `DragSortCursorAdapter` family, `LiftAnimator` — never constructed, its field assignment is commented out), two more `DEBUG`-style compile-time-constant branches (`Mp4File.PRINT_DEBUG = false`, matching the `MediaLibraryBackend.DEBUG` one found in an earlier session), several unused convenience constructors of views built only from XML (`SlidingTabLayout`, `VanillaTabLayout`, `VanillaImageButton`, `SlidingView`, `FastScrollGuardedListView`), `Song.compareTo` / `toString` (the `Comparable` interface is implemented but never used — `SongTimeline` sorts with its own two `Comparator`s instead), `ThemeHelper.usesDarkTheme` and `Common.debug` (dead private/unused helpers), and both halves of the `Checkable` delegation chain (`DraggableRow.isChecked`/`toggle`, `DragSortItemViewCheckable.isChecked`/`toggle`) after reading `AbsListView.java` / `ListView.java` and confirming the framework's row-check-state update machinery calls only `setChecked`, never `isChecked` or `toggle`, on a bound row view.

## How the checked paths were chosen

`python3 -I tools/verify_sample.py Vanilla-Music 30` (seed 20261025) picked 30 reachable methods by stratum (a non-standard edge, an inferred label, a STATE gate, an ENV gate, a long route, the plain rest), each one adding the most previously-unseen edges to the covered set first: 30 methods whose routes cover 266 of the distinct edges on all best routes. Every step of every one of the 30 was read with `tools/show_route.py` (a local copy with one parsing bug worked around, see Limits) against the cited source lines, including the enclosing `if` / `switch` / `catch` conditions of each bytecode-cited call. The sample was redrawn after the onResume fix (the route costs changed) and again after the drag-remove guard fix, and the final 30 were re-read against the final build. 4 of the 30 had an error in them when first read (the onResume conflation, the two citation line bugs, and the guard-less drag-remove chain — counted as 3 distinct findings since one of them, the citation bug, surfaced through two different sampled routes); all 4 are fixed. 19 of the 30 are logged `fixed` because their route runs through the onResume fix even though they themselves read correct once it was applied (same convention `make_vlog_omni_notes.py` uses for a systemic fix). Error rate (fixed + wrong) / (correct + fixed + wrong) = 19 / 30 ≈ 0.63, all of it attributable to the one systemic onResume bug plus a handful of independent citation slips; no route was left wrong.

## What waits for a device (API 27)

- **Device run 41593209101-1 (2026-11-03, Google APIs, API 27, x86).** 8 of 30 routes reached their target method; 5 of them ran the whole script and are now `DEVICE_OK`. 3 more reached the method although the script stopped early; their path keeps its earlier status. The other routes are unclear (not reached, script stopped, or unscriptable), never wrong; the reason for each route is in `handoff/DEVICE_RUN_SUMMARY.md`. What is listed below still waits for a device.

- **The launcher's handling of the four home-screen widgets** (`OneCellWidget`, `FourLongWidget`, `FourSquareWidget`, `FourWhiteWidget`, plus `WidgetD`/`WidgetE`): placing a widget, resizing it, and removing it are done by the launcher app (another process); its source was not read, so the `other_app` ENV gate on every widget method is as far as this audit goes.
- **The runtime storage-permission dialog itself** (`PermissionRequestActivity` only starts it and reads the result; the system permission UI is another app/process) and whether the OS actually re-delivers `onRequestPermissionsResult` exactly as `Activity.java` describes on a real API 27 image.
- **IME behaviour** for every text field (the search box, the playlist name dialog, the jump-to-time dialog, the folder-browser path field): the soft keyboard is not part of this app and was not read.
- **Bluetooth / headset media-button delivery and the exact `AudioManager` focus-change timing**, both outside the app process.
- **The JobScheduler's actual timing** for `ScheduledLibraryUpdate` (charging + idle + ~32 h period): the constraints were read from the source, not observed on a device.
- **The real ContentObserver delivery of a MediaStore change** from the platform media scanner (`MediaScanner$1.onChange`): the platform-side scanner and provider were not read, only the registration side.

## Hazard candidates (from reading the code, not reproduced)

- `PermissionRequestActivity.onRequestPermissionsResult` calls `android.os.Process.killProcess(android.os.Process.myPid())` after granting the permissions (PermissionRequestActivity.java:84-86), by design, to force a fresh process per the comment at lines 81-83; a device replay has to expect the whole app process to die and restart here, not a crash.
- `DragSortController.onTouch` dereferences `mDslv` (the `DragSortListView`) inside the `ACTION_UP` branch without a null check once a drag is in progress (DragSortController.java:261-268); nothing in the read call graph detaches `mDslv` during a drag, but this was not exercised on a device.
- `FileSystemAdapter.query` (FileSystemAdapter.java:188-205) calls `file.listFiles(mFileFilter)` on the current browse directory and, on `null` (a removed or unreadable directory — for example the SD card was ejected mid-browse), falls back to `FileUtils.getFallbackDirectories`; a race between a permission revoke mid-session and this call was not reproduced.
- `CoverCache$BitmapDiskCache.put` (CoverCache.java:340-356) stores a lossily re-compressed JPEG of every cover art bitmap ever shown, keyed only by `hashCode()` (not `equals()`), in `covercache.db`; a hash collision between two different `CoverKey`s (different media type/id/size) would silently return the wrong cached cover. Not reproduced; `CoverKey.equals()` is implemented but the disk cache never calls it (confirmed by reading `get`/`put`), only `LazyCoverView$CoverMsg.isRecent()` uses `equals()`, for an unrelated in-memory staleness check.

## Limits

- `tools/show_route.py` crashes (`ValueError: invalid literal for int() with base 10`) on several routes in this app: its evidence-reference regex stops at the first space inside a citation like `SRC File.java:403, 408-424` (a space-separated second range after a comma), leaving a trailing comma that `int()` rejects. This is a pre-existing tool bug (reported to the orchestrator, not fixed here — out of scope), reproducible on e.g. `show_route.py Vanilla-Music "PlaybackActivity.onOptionsItemSelected@PREFS"`. Worked around for this session by a local read-only copy of the script (in the scratchpad, not under `work/tools/`) that only changes the reference-splitting regex to keep a comma-separated range list together; every route in `verification.csv` was read with that copy against the same cited source lines `show_route.py` would have shown.
- Without the androidx (`ViewPager`, `MediaSessionCompat`) source, the tab-strip paging and the media-session callback dispatch stay `INFERRED` (315 of 1473 labels); this matches the pattern already noted for the other apps in this project.
- The derived best route minimises ENV gates, then STATE gates, then steps, and ignores guards; only the 30 sampled routes (plus the one read before the sample was redrawn) were checked step by step against the source. A method's reachability does not depend on `sanity_check.csv` (tool coverage): 4 contradictions are listed there (`Song.compareTo`, `Song.toString`, `DragSortController.setSecondaryOnTouchListener`, `DragSortListView.setOnTouchListener` — all UNREACHABLE but ran in a Monkey/APE session) and left as UNREACHABLE per this audit's own grep-confirmed reasoning (no caller of any of the four anywhere in the app or library sources), not flipped by the tool run; a tool hit on a method with no source-confirmed caller is left unexplained rather than used to relabel it.
- Context variants for `onResume` (`@LibraryActivity` etc.) model which activity is resuming, not which page was open before a rotation or process restart; a real device replay that kills the process mid-session could expose a gap here that source reading cannot.

## JSON shape (short)

```
{ "schema": 2, "title", "screens": {page: description}, "methods": [...], "verdict": {method: REACHABLE|UNREACHABLE},
  "labels": {method: {unreachable: {kind, text}, env: [{kinds, text}], state: [{kinds, text}], route_edge_classes, explicit_standard_route,
                      confirmed_by, source_ref, path_status}},
  "edges": [ {id, src, dst, kind, edge_class, via, trigger, gui[], guard, reads[], writes[], note, needs_state, state_kinds, env, env_kinds, evidence, class_basis} ],
  "paths": [ {method, edges[], edge_classes, explicit_standard_only, env, state, verified_by, ref} ], "verification": {...} }
```

`src`/`dst` are methods (`Class.method`, overloads as `Class.method(Type,Type)`) or pages (`S_...`). A suffix `@CONTEXT` is the same method or page in a specific context. Edge ids are a hash of the edge content, so they stay stable when other edges change.
